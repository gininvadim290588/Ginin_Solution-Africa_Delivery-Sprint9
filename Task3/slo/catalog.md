# Контракт качества каталога

**Проект SLA/SLO. Сервис: каталог Africa Delivery. Владельцы: CTO и CEO.**

Каталог должен показывать разрешённые товары и быстро отвечать. Цели считаются отдельно для Нигерии и Кении. SLI — результат измерения, SLO — цель команды, SLA — согласованное обещание бизнесу.

## SLI — что и как измеряем

| Показатель | Что считается успехом | Как считаем |
|---|---|---|
| Успех запросов | Корректный ответ HTTP 200 на список или карточку; товар разрешён, копия не старше установленного срока | Успешные запросы / все учитываемые запросы × 100% |
| Доступность по времени | Минутная внешняя проверка списка и контрольной карточки через публичный адрес завершилась корректно за ≤5 с | Успешные минутные проверки / запланированные проверки × 100% |
| Скорость | Запрос завершился корректно за ≤1 с | Быстрые успешные запросы / все учитываемые запросы × 100%; дополнительно P99 |

Учитываем реальные GET-запросы к списку и существующим карточкам, дошедшие до публичного входа. Ошибки 5xx, тайм-ауты, неверное содержимое и отклонение легитимного запроса из-за нехватки мощности — неуспех. Заведомо неверный запрос, подтверждённая атака и тестовая нагрузка вне испытаний исключаются по заранее определённому правилу; исключения видны в отчёте.

Измерение начинается на публичном входе и заканчивается отправкой ответа. Время отсутствия связи на телефоне сюда не входит. Внешние проверки дополнительно обнаруживают проблемы адреса сайта, сертификата и входной сети.

При отсутствии пользовательского трафика показатель запросов имеет значение «нет данных», а не 100%. Пропущенная минутная проверка не считается успешной.

## SLO — цели команды

| Показатель | Цель за последние 30 суток | Бюджет ошибок |
|---|---:|---|
| Успех запросов | ≥99,9% | ≤0,1% запросов |
| Доступность по минутным проверкам | ≥99,9% | 43,2 плохой минуты; максимум 43 целые проверки |
| Быстрые успешные запросы | ≥99% за ≤1 с | ≤1% запросов; P99 ≤1 с |

Тайм-ауты и ошибки не исчезают из оценки скорости: доля быстрых успешных ответов обязательно показывается рядом с P99. Запланированные обновления тоже расходуют бюджет ошибок.

## SLA — что предлагаем гарантировать

После утверждения CEO и CTO: **не менее 99,5% успешных запросов и отдельно минутных проверок за календарный месяц UTC**, круглосуточно. Правила успеха и исключений совпадают с SLI. Это более слабый договорный предел, чем внутренняя цель 99,9%.

При общем отказе дежурный вызывается после двух плохих минут подряд и подтверждает вызов за 5 минут. Команда сообщает бизнесу статус каждые 30 минут. При нарушении SLA готовит разбор причин и меры в течение двух рабочих дней; CEO отвечает за сообщения покупателям. При исчерпанном SLO-бюджете обычные релизы останавливаются до восстановления запаса, кроме исправления инцидента.

Денежные компенсации не выдумываются архитектурой: их условия CEO и CFO должны утвердить до публичного обещания. Пока соглашение не подписано, это проект обязательства.

## Карточка по модели OpenSLO

| Поле | Значение |
|---|---|
| apiVersion / kind | `openslo/v1` / `SLO`; отдельная цель для каждого показателя |
| service | `catalog-ng` или `catalog-ke` |
| metadata.name | Отдельные цели `catalog-requests`, `catalog-time`, `catalog-latency` для каждой страны |
| indicator | Доли из таблицы SLI; источник — публичный вход и независимые проверки |
| objectives | 0,999 / 0,999 / 0,99 соответственно |
| timeWindow | `30d`, скользящий период |
| timeSliceWindow / timeSliceTarget | Для минутных проверок: 1 мин / 1,0; проверка целиком успешна либо нет |
| budgetingMethod | `Occurrences` для запросов; `Timeslices` для минутных проверок |

Это Markdown-описание по [модели OpenSLO](https://openslo.com/specification/), не готовый YAML-манифест. Договорный SLA описан отдельно: OpenSLO задаёт цели измерения.

- Порог 1 с для P99 усиливает прежнюю цель Task2 для P95. Его подтверждают нагрузочным тестом.

- Для страны работают две копии приложения и независимый проверяющий узел.
