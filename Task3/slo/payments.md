# Контракт качества оплаты

**Проект SLA/SLO. Сервис: оплата Africa Delivery. Владельцы: CTO, CFO и CEO.**

Собственная платформа принимает заявку и ведёт учёт. M-Pesa или Flutterwave исполняют платёж. Поэтому отдельно измеряем надёжность собственного API и результат всей попытки оплаты. API — интерфейс обмена данными; PSP — лицензированный платёжный партнёр.

## SLI — что и как измеряем

| Показатель | Что считается успехом | Как считаем |
|---|---|---|
| Собственный API | Заявка сохранена в БД и получен корректный ответ; запрос статуса возвращает достоверное состояние | Успешные запросы / все учитываемые запросы × 100% |
| Доступность по времени | Минутная проверка записи контрольной заявки и чтения статуса через публичный вход прошла за ≤5 с | Успешные проверки / запланированные проверки × 100% |
| Скорость приёма | Корректный приём заявки или чтение статуса завершены за ≤1,5 с | Быстрые успешные запросы / все учитываемые запросы × 100%; дополнительно P99 |
| Итог с участием PSP | Не позднее 300 с после принятой попытки известен проверенный итог: оплачено, отказано или подтверждённо отменено | Попытки с таким итогом / все учитываемые попытки × 100% |
| Финансовая целостность | Повтор запроса/сообщения не повторил списание, выплату или выдачу | Число повторных финансовых действий |

Для собственного API учитываем корректные запросы авторизованных покупателей. Ошибки нашей системы, потерянная запись, тайм-аут и недостаток мощности — неуспех. Подтверждённое отклонение неверных данных не является техническим отказом. Незавершённая операция не получает статус «оплачено».

**Ответ «заявка принята» не означает списания денег.** Итоговую оплату подтверждает проверенное сообщение PSP или проверка его отчёта. Отказ банка — достоверный итог, но не успешная продажа; конверсию оплаты показываем отдельной бизнес-метрикой.

В полный путь входят задержки и отказы PSP, потерянные подтверждения и повторная доставка. Их нельзя убрать из отчёта как чужую проблему. Для этого показателя оцениваем 30 суток попыток, завершившихся по сроку проверки: окно заканчивается на 5 минут раньше текущего времени. Позднее подтверждение не превращает нарушение срока в своевременный успех.

Контрольная заявка не вызывает настоящее списание. Она проверяет только собственный путь. Реальное исполнение PSP измеряется по настоящим попыткам. Пропуск минутной проверки — неуспех; отсутствие запросов — «нет данных».

## SLO — цели команды

| Показатель | Цель | Бюджет ошибок |
|---|---:|---|
| Успех собственного API, 30 суток | ≥99,9% | ≤0,1% запросов |
| Минутные проверки, 30 суток | ≥99,9% | Максимум 43 плохие проверки |
| Быстрые успешные запросы, 30 суток | ≥99% за ≤1,5 с | ≤1%; P99 ≤1,5 с |
| Достоверный итог до 300 с, 30 суток | ≥99% | ≤1% попыток |
| Повторные финансовые действия | **0** | **Не допускаются** |

Нельзя потратить бюджет ошибок на двойное списание. При неопределённом исходе сохраняем номер операции и проверяем её статус; не повторяем списание вслепую и не переносим его другому PSP.

## SLA — что предлагаем гарантировать

После утверждения: **≥99,5% успешных собственных запросов и отдельно минутных проверок за календарный месяц UTC**. Финансовые действия не повторяются из-за наших повторов обработки; цена и факт оплаты не берутся из кеша.

Цель результата до 300 с пока не является договорной гарантией PSP: для неё нужны подтверждённые условия маршрута. CFO и CEO заключают договоры, CTO проверяет интеграцию. Даже при соблюдении собственного SLA полный путь может нарушить SLO — это отдельный инцидент, который остаётся в отчёте.

При подозрении на двойное списание или ложный статус «оплачено» — немедленный вызов дежурного и CFO, остановка затронутых операций, сверка по номеру и сумме. Неизвестные исходы направляются оператору после 300 с. Сверка затронутых оплат после восстановления — до 24 ч.

Общий отказ вызывает дежурного после двух плохих минут подряд; подтверждение вызова ≤5 мин, статус бизнесу каждые 30 мин, разбор причин ≤2 рабочих дней. Компенсации покупателям согласуют CEO/CFO. SLA остаётся проектом до утверждения.

## Карточка по модели OpenSLO

| Поле | Значение |
|---|---|
| apiVersion / kind | `openslo/v1` / `SLO`; отдельная цель для каждого показателя |
| service | `payments-ng` или `payments-ke` |
| metadata.name | Отдельные цели `payments-requests`, `payments-time`, `payments-latency`, `payments-outcome` |
| indicator | Соответствующие доли из SLI; источник — входной сервер, БД операций, подтверждения PSP |
| objectives | 0,999 / 0,999 / 0,99 / 0,99 |
| timeWindow | `30d`, скользящий период; итоговые события оцениваются с задержкой 300 с |
| timeSliceWindow / timeSliceTarget | Для минутных проверок: 1 мин / 1,0; проверка целиком успешна либо нет |
| budgetingMethod | `Occurrences`; для минутных проверок — `Timeslices` |

описание по [OpenSLO](https://openslo.com/specification/); правило нулевых дублей проверяется отдельно, а не маскируется средним процентом.

## Assumptions

- M-Pesa применяется в Кении, Flutterwave — в Нигерии. Paystack не включён в пилот по [Task2, раздел 2](../../Task2/architecture-vision.md#2-устройство-системы-и-ответственность).
- Повтор вызова списания разрешён только при документированной защите PSP от дубля с тем же номером операции. До проверки используем запрос статуса и ручную сверку.
- Итог за 300 с и SLA 99,5% — предложенные цели; договоров и статистики PSP нет.
- При потере площадки RPO до 15 минут требует сверки. Сомнительные финансовые действия ограничиваются до подтверждения; это отражается в полном пути оплаты.
