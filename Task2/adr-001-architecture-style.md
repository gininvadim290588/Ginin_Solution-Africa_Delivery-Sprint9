# ADR-001 — Выбор архитектурного стиля

**Встреча в Найроби ориентировочно 17.08. Решение предложено к утверждению.** Автор: архитектор. Владельцы: CTO — техника, CEO — объём, CFO — расходы; инвестор меняет дату/обещания. Правовые ограничения не отменяются голосованием (А3).

## Контекст

MVP NG/KE: 100 продавцов/5 000 SKU, заказ, M-Pesa/Flutterwave, уведомления, кабинет/отчёты (кейс; А8). А5, с.1–3 требует 10М пользователей сразу, 40–50 сервисов/три кластера, Oracle, свою логистику. А6, с.1 допускает $5К/мес регулярной техники, ≤6 контракторов, без годовых предоплат. Команда/нагрузочный профиль не подтверждены (Task1, C04–C05; Canvas 6–9).

Открытие **15.10.2026** фиксировано (А1, с.1; А7). Начало проекта — **10.08.2026**: при старте работ в этот день план A на восемь недель заканчивается **05.10**, оставляя **10 календарных дней** до открытия. B на 12 недель заканчивается 02.11, C на 24 недели — 25.01.2027; опоздание составляет 18 и 102 дня. Готовность команды и договоров не подтверждена: задержка старта уменьшает резерв. Если реализация начнётся только после встречи 17.08, A заканчивается 12.10 и оставляет три дня. Основание дат и допущения — [календарь кейса](../case-calendar.md).

## Решение

**Модульный монолит Go/PostgreSQL + фоновый процесс**, отдельные национальные контуры NG/KE. Модули: каталог/остатки, заказы, расчёты, доставка, уведомления, управление/отчёты. Транзакционное ядро, идентификаторы повторов, события сохраняются с операцией и повторно доставляются; границы контрактов — сейчас, сетевое разделение — позже (А8; А5).

**Partner/buy:** лицензированные PSP, сообщения и перевозчики; собственные правила торговли/сверка/адаптеры. M-Pesa KE, Flutterwave NG; Paystack после MVP. Sendbox/Sendy — кандидаты; действующий API KE проверяет CEO. Не строим банк/кошелёк/курьерский движок. Минимальная модерация/возвраты обязательны даже без полного бэк-офиса (А1, с.3; А3, с.2; А4; А8).

Контейнеры, автоматизация, метрики/trace IDs, локальные копии — сразу. Один провайдер на страну; восстановление на альтернативной разрешённой среде проверяет переносимость. Одновременное мультиоблако, mesh/Kafka/Kubernetes и платную Oracle не принимаем для пилота (А5; А6).

## Последствия

A упрощает согласованность/эксплуатацию, сокращает ошибочные вложения. Минусы: общий релиз/БД увеличивают область отказа; независимое масштабирование сложнее; дежурства тяжёлы для шести FTE; партнёры добавляют комиссию/зависимость. Выделение сервисов **$120К в Год 3** уже в TCO, сверх обычного ФОТ.

99,99%/RPO=0 без деградации **не гарантируются**. Предложение пилота: 99,9% платформенных запросов, RTO≤60/RPO≤15 мин при потере площадки; финансовые подтверждения при разделении сети ждут согласованности. Внешний PSP/полный путь измеряем отдельно. Это явное исключение инвестора; **без него no-go**, не незаметная замена требования (А1; А5; Task1, технический предел).

## Late binding и проверка

Выделять модуль при нарушении согласованного p95 после настройки/разрешённого увеличения мощности либо ≥2 команды теряют >20% времени на общий релиз. Kubernetes/mesh — ADR при ≥10 процессов/≥2 SRE; Oracle — после доказанного ограничения БД/оферты. Active-active — после сценария отказов/законных площадок/бюджета. На августовской встрече CTO называет программу CNCF: Certified Kubernetes не сертификат маркетплейса (А5; официальный источник в сравнении).

B2B/AI/кошелёк/видео/live-shopping/iOS/языки — business case после 90 дней пилота; CEO исправляет А2. Токены отложены по А1, с.3/А5, с.3. **14.10 go/no-go:** договоры/правовой допуск/комиссия <2,5%, публикация, покупка/сверка/возврат/выдача, повтор webhook, восстановление/нагрузка. Ограниченное событие 15.10 без этих доказательств не называется MVP (А3; А6).

## Assumptions

Начало кейса подтверждено А1; 17.08 как дата встречи и старт работ 10.08 — плановые допущения. TCO SA-01–11: прогноз/ставки/сроки — оценки, не оферты; Oracle EE/4 Processor предположены, редакции в А5 нет. До местного заключения PII/логи/копии не экспортируем как предосторожность (А3). Новые SLO/триггеры не утверждены.
